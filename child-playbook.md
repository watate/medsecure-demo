## Overview

Fix a batch of CodeQL security alerts in a repository. You will receive a specific list of alerts with rule IDs, file paths, line numbers, and descriptions. Create a branch, fix every alert in your batch, validate the fixes, and open one PR.

## Procedure

1. **Clone and branch**: Clone the repo, check out the default branch, and create the branch name provided in your prompt.

2. **Read and understand**: Open every file referenced in your batch. Read each file fully, plus closely related files (imports, callers, tests). Look for existing sanitization helpers, validation utilities, or wrapper functions you should reuse.

3. **Fix each alert**: Work through alerts file by file, top-to-bottom by line number within each file.
   - Apply minimal, targeted fixes that address the root cause.
   - Common patterns: parameterized queries for SQL injection, context-appropriate escaping for XSS, path canonicalization for traversal, safe deserialization with type checks, environment variables for hard-coded secrets, null guards for missing checks.
   - If multiple alerts share a root cause, fix the root once rather than patching each usage independently.
   - If an alert requires an architectural change you cannot safely make, skip it and record: `SKIPPED: alert #<number> — <reason>`.

4. **Validate**: Run the repo's test suite and linter. If your changes break tests, fix them. If you cannot fix a test failure, revert that specific fix and mark it SKIPPED.

5. **Commit and push**: Use clear commit messages referencing alert numbers. You may use one commit per file or one commit for all changes, whichever is cleaner.

6. **Open a PR**:
   - **Title**: Generate a descriptive title based on the actual vulnerabilities you fixed. Use this format:

     `fix(<scope>): <what you fixed> [CodeQL/Devin]`

     Where:
     - `<scope>` is the short module or directory name (e.g., `auth`, `api`, `models`, `utils`)
     - `<what you fixed>` is a human-readable summary of the vulnerability types you addressed
     - `[CodeQL/Devin]` is always appended so reviewers know it's automated

     Good examples:
     - `fix(auth): SQL injection in login and session queries [CodeQL/Devin]`
     - `fix(api): hardcoded credentials in config loader [CodeQL/Devin]`
     - `fix(templates): XSS via unsanitized user input in 3 templates [CodeQL/Devin]`
     - `fix(models): insecure deserialization in payment processing [CodeQL/Devin]`

     Bad examples (never use these):
     - `fix(security): resolve CodeQL alerts — batch 1 of 13`
     - `Fix security issues`
     - `CodeQL remediation batch 3`

     If the batch covers multiple unrelated vulnerability types, lead with the highest-severity one and mention the count:
     `fix(api): SQL injection + 2 other vulnerabilities [CodeQL/Devin]`

   - **Body** must include: a summary of the fix approach, a table with columns `Alert # | Rule | File | Line | Fix Applied`, any skipped alerts with reasons, and the footer `> Generated by Devin — CodeQL auto-remediation`
   - Add `security` and `automated` labels if they exist in the repo.

## Advice & Pointers

- Read all affected files fully before making any changes.
- Respect existing codebase patterns. Use existing helpers and wrappers.
- Multiple alerts often share a root cause. Fix the source, not each sink.
- If your fix requires a new third-party dependency, mark the alert SKIPPED with reason `requires new dependency: <package>` and recommend the fix in the PR body.
- Every changed line should trace back to an assigned alert.

## Forbidden Actions

- Do not merge the PR. Leave it for human review.
- Do not modify code unrelated to your assigned alerts.
- Do not suppress alerts with lgtm comments, nosec comments, SuppressWarnings annotations, or any equivalent. Fix the root cause.
- Do not commit secrets, tokens, or credentials.
- Do not delete or disable existing tests.
- Do not force-push.
- Do not push directly to the default branch.
- Do not fix alerts outside your assigned batch.
